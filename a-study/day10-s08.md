# 第10天：s08 Context Compact 阈值实验

今天只解决一个核心问题：

> 当上下文真正超过阈值时，Harness如何把完整历史变成“当前请求 + 状态摘要”，并继续保留可追溯的原始记录？

建议投入 **75～90分钟**。

第9天已经理解并离线验证前三层：大结果落盘、中间历史归档、旧结果占位。今天专门验证第四层`compact_history`和补救层`reactive_compact`。

## 今日定位

- 所属层：Harness上下文管理层
- 解决问题：确定性裁剪之后，历史仍然超过上下文预算
- 接入位置：每次模型调用前，以及API返回上下文过长错误后
- 重要程度：核心
- 今日深度：看见摘要替换前后的结构变化，不研究摘要Prompt优化

总流程：

```text
prepare(messages)
→ 前三层确定性整理
→ estimate_chars仍超限
→ 保存完整transcript
→ 调用摘要器
→ history替换为一条压缩消息
→ 继续原任务
```

## 今日可见成果

今天结束时必须看到：

1. 降低阈值后自动触发`compact_history`
2. 压缩前后字符数明显下降
3. 原始历史完整写入transcript
4. 压缩消息同时包含当前用户请求和历史摘要
5. `reactive_compact`保留最近消息，只总结较早历史
6. 摘要失败或二次超长不会无限重试

## 为什么今天仍不完整迁移OpenAI

当前`s08`压缩器识别的是Anthropic消息结构：

```text
assistant(content=[tool_use])
user(content=[tool_result])
```

OpenAI Responses使用：

```text
function_call
function_call_output
```

完整迁移不仅是替换SDK，还必须改写：

- 工具调用和结果识别
- `call_id`配对保护
- 新旧结果判断
- 批量结果预算
- transcript序列化

这属于协议适配项目，不是今天理解压缩策略的必要条件。今天使用假摘要器，不产生API费用，也不受供应商协议影响。

## 40～55分钟：观察自动摘要

运行实验，确认：

```text
压缩前：多条历史消息，字符数超过阈值
       ↓
[auto compact]
       ↓
完整历史写入transcript
       ↓
FakeClient返回固定摘要
       ↓
压缩后：通常只剩一条summary_message
```

压缩消息应类似：

```text
[Compacted]

Current user request:
当前真正要完成的任务

Conversation summary (reference only):
历史状态摘要

Full transcript:
完整历史文件路径
```

检查`active_request`不是从最后一条`role=user`猜出来的，而是单独传入。

## 55～65分钟：观察补救压缩

阅读并运行`reactive_compact()`实验。

它的触发场景：

```text
字符估算认为没超限
→ API仍返回prompt_too_long
→ 保存transcript
→ 总结较早历史
→ 最近5条消息原样保留
→ 重试一次
```

对比：

| 方法 | 何时发生 | 保留策略 |
|---|---|---|
| compact_history | 主动估算超限或模型调用compact | 用一条摘要替换整个历史 |
| reactive_compact | API明确拒绝上下文 | 摘要较早历史并保留最近消息 |

检查`MAX_REACTIVE_RETRIES = 1`：同类错误再次出现时应抛出，而不是无限压缩重试。

## 65～75分钟：理解主动compact工具

只追踪：

```python
COMPACT_TOOL
compact_requested
```

关键顺序：

```text
一次模型响应包含write_file和compact
→ 两个工具请求都先得到对应结果
→ 完整批次闭合
→ 再执行历史压缩
```

不能遇到`compact`就立刻清空历史，否则同一批次其他工具调用可能失去结果配对，文件副作用也可能被模型重复执行。

